# 04. 監査ログ仕様書

> 設計段階の記載（[README の注記](./README.md)）。

---

## 1. この文書が答える問い

情シスは「監査ログは取れますか」と聞く。
本プロダクトは [00 原則3](../design/00-overview.md) で「在席ログを残さない」と決めている。
**一見、矛盾する。**

矛盾しない。**境界を引いてあるからである。**

> **セキュリティ監査に必要なログはすべてあります。
> 従業員の監視に使えるログはありません。**

情シスが本当に欲しいのは前者であり、後者を求めているのは（もしいるなら）情シスではない。

---

## 2. 残すもの / 残さないもの

| 残す（監査に必要） | 残さない（監視に使える） |
| --- | --- |
| ログイン成功・失敗（誰が、いつ、どの IP から） | 誰がどのフロアのどこに何分いたか |
| 管理操作（メンバー追加・削除・権限変更・設定変更） | 誰と誰が何分話したか |
| データのエクスポート実行 | 個人のオンライン時間・稼働率 |
| プライベートルームの**作成**と**招待操作の事実** | プライベートルームの**中で何が起きたか**、**誰を招待したか**（§3） |
| フロアのマップ定義の変更 | 発話量・レスポンス速度・既読 |

---

## 3. 記録する操作の一覧（これがすべて）

```
LOGIN_SUCCESS          ログイン成功
LOGIN_FAILURE          ログイン失敗
MEMBER_INVITED         メンバーを招待した
MEMBER_DEACTIVATED     メンバーを無効化した（退職処理）
ROLE_CHANGED           ロールを変更した
SPACE_MAP_UPDATED      フロアのマップ定義を変更した
ORG_SETTINGS_UPDATED   組織設定を変更した
PRIVATE_AREA_CREATED   プライベートルームを作成した
PRIVATE_AREA_INVITE    プライベートルームへの招待操作を行った（※）
DATA_EXPORTED          データをエクスポートした
```

**この10個がすべてである。** ここに値を足すことは、上の境界線を破ることを意味する。

### ※ `PRIVATE_AREA_INVITE` の設計変更

当初は「誰をどの部屋に招待したか」を残す設計だった。
しかし**それは1年間残る「誰と誰が一緒にいた記録」であり、原則3と衝突する。**

→ **招待先の部屋 ID と被招待者を記録しない形に変更した。**

| 記録する | 記録しない |
| --- | --- |
| 誰が、いつ、招待操作を行ったか | どの部屋に |
| | 誰を |

権限変更の追跡（「管理者以外が招待操作をしていないか」）には足りるが、
**人間関係の復元には使えない。**

> この変更は、この文書を書く過程で見つかった穴の修正である
> （[README §書いて分かったこと](./README.md)）。

## 4. レコードの形式

```
{
  id        : 一意の識別子
  orgId     : 組織
  actorId   : 操作した人（ログイン失敗時は null になりうる）
  action    : 上記10種のいずれか
  targetId  : 操作対象（メンバーID など。該当しない場合は null）
  ip        : 送信元 IP
  createdAt : 発生時刻（UTC）
}
```

- **本文・内容・位置・時間の長さを持つフィールドは無い**
- `targetId` に部屋 ID や会話 ID は入らない

## 5. 誰が読めるか

| 役割 | 監査ログの閲覧 |
| --- | --- |
| MEMBER | ❌ |
| ADMIN | ✅ 自組織のみ |
| 提供側（SaaS 運用者） | 障害対応時のみ、記録を残して実施 |
| **誰であっても** | ❌ 「残さないもの」の列は**データもAPIも無い** |

エクスポート: CSV / JSON。SIEM への取り込みを想定した形式にする。

---

## 6. 保持期間

| | 既定 | 変更 |
| --- | --- | --- |
| 監査ログ | **1年** | 組織設定で 90日 / 1年 / 3年 |

期間経過で自動削除する。**延長は監査要件に合わせて顧客が決める。**

---

## 7. 「作らない」を仕組みで守る

**「作らない」判断は、実装中に「便利だから」という理由で簡単に覆る。**
仕組みで守らなければ必ず崩れる（[06 リスク R-8](../design/06-roadmap.md)）。

| 守り方 | 内容 |
| --- | --- |
| 書き込み経路の集約 | 監査ログへの書き込みを1つのモジュール（`audit.ts`）に集約する。他の場所から書けない |
| **CI で検知** | §3 の一覧に値を追加する変更、および [03 §2](./03-stored-data.md) の「保存しないもの」に該当するテーブルの追加を、CI が検出する |
| レビュー必須 | 上記を含む変更は、**設計ドキュメントの更新を伴わない限りマージしない** |
| マイグレーション監査 | すべてのマイグレーションをレビュー対象にする |

**この節が、この文書の中で一番重要である。**
仕様書に何と書いても、コードが違うことをしていれば意味がない。
