## 導入形態

**Q1. 端末に何かインストールしますか。**
いいえ。ブラウザだけで動きます。管理者権限も不要です。
Chrome / Edge / Safari の最新2バージョンに対応します（Firefox は best effort）。

**Q2. スマートフォンでも使えますか。**
はい。ただし空間内を動くのはデスクトップを想定した機能です。
モバイルでは、フォーカスカードとチャットの閲覧が主な用途になります。

**Q3. オンプレミス / 自社クラウドに置けますか。**
はい。**構成要素はすべて OSS で選定してあり、これが主要な導入形態の一つです。**
[01 §2](./01-endpoints.md) の3サーバ構成で、外向き通信は認証だけになります。

**Q4. 社外の人を招けますか。**
v1 ではできません。同一メールドメインのメンバーのみです。
時間制限つきのゲスト招待は将来の検討項目です（[03 C-03](../design/03-features.md)）。

## ネットワーク

**Q5. 何を許可リストに入れればよいですか。**
[01 §1.1](./01-endpoints.md) の表をそのままお使いください。**5行**です。
うち認証用の1行は、Google Workspace / Microsoft 365 をお使いなら既に許可済みのはずです。

**Q6. UDP は開けられません。動きますか。**
**動きます。** TCP 443（TLS）の TURN に自動でフォールバックします。
HTTPS と同じポート・同じ見え方なので、SSL インスペクション環境でも通ります。
遅延は増えますが通話は成立します。

**Q7. それでも通らない環境ではどうなりますか。**
**テキストモードに縮退します。** 空間とフォークスカードとチャットは使えて、
通話は既存の Zoom / Teams にお任せする形です（1人あたり 5 kbps 程度）。
「まったく使えない」にはならない設計です。

**Q8. 導入前に自社環境で動くか確認できますか。**
確認ツールを提供予定です（[03 M-19](../design/03-features.md)、Phase 1）。
UDP 到達性・TURN 疎通・WebSocket の安定性・往復遅延・推定帯域を判定し、
**情シス向けのレポートを PDF で出力**します。
**現時点では未実装です。**

**Q9. 帯域はどれくらい必要ですか。**
100人・同時通話20%で **約 1.6 Mbps** です。計算式は [01 §3](./01-endpoints.md)。
既定でビデオを OFF にしているため、一般的なビデオ会議ツールより1桁小さくなります。

**Q10. 社内にポートを開ける必要はありますか。**
ありません。すべてクライアントからの発信です。

## 暗号化・盗聴

**Q11. 通信は暗号化されますか。**
はい。HTTP / WebSocket は TLS 1.3、音声・映像は DTLS-SRTP です。
**加えて、音声は E2EE（AES-GCM 256）を既定で有効にします。**

**Q12. TURN サーバを経由すると中身を見られませんか。**
**見られません。** DTLS-SRTP の鍵交換と復号は端点（ブラウザ）でのみ行われ、
TURN は暗号化パケットを中継するだけで鍵を持ちません。
鍵素材は JavaScript からも取り出せません。

**Q13. サーバ側で音声を復号できますか。**
**E2EE を有効にしている音声とプライベートルームは、できません。**
E2EE を無効にした映像については、SFU で一度復号されます（SFU 方式の性質です）。
セルフホストの場合、その SFU は御社のサーバです。

**Q14. なぜ E2EE を既定にできるのですか。他社は難しいと言います。**
E2EE を有効にするとサーバ側の録画・文字起こし・映像合成ができなくなります。
**本プロダクトはそれらを最初から作らないと決めているため、失うものがありません。**
一般的なビデオ会議 SaaS が E2EE を既定にできないのは、それらを機能として売っているからです。

**Q15. E2EE の限界を教えてください。**
正直にお答えします。

- **メタデータは隠せません。** 「誰がいつどの room にいたか」はサーバから見えます。
  ただし**保存しない**設計なので記録としては残りません（運用者がリアルタイムに観測することは原理的に可能です）。
- **ブラウザの E2EE は配信される JavaScript に依存します。** サーバが改竄した JS を配れば無意味になります。
  CSP と SRI で緩和しますが、**完全な解決策は存在しません**。これはブラウザ製品すべてに共通する構造的限界です。
- **端末が侵害されたら無意味です。** マルウェアや画面録画には勝てません。

これらが受け入れられない場合は、**セルフホストをご検討ください**（運用者が御社自身になります）。

**Q16. 参加者同士に IP アドレスは漏れませんか。**
漏れません。P2P ではなく SFU 経由なので、ICE 候補は SFU のアドレスに解決されます。
在宅勤務の自宅 IP が同僚に見えることはありません。

**Q17. 社内 CA の証明書でも動きますか。**
WebRTC は**有効な証明書を持つ HTTPS 接続**を要求します。
社内 CA の証明書でも動きますが、**全端末に配布済みであることが条件**です。
自己署名のままでは動きません。

## 認証・権限

**Q18. SSO は必須にできますか。**
はい。**SSO 以外の認証手段を持ちません。** パスワードを保存していません。
Google Workspace / Microsoft 365 の OIDC に対応します。

**Q19. MFA や条件付きアクセスは効きますか。**
はい。認証はすべて御社の IdP に委ねているため、IdP 側の設定がそのまま適用されます。

**Q20. ドメイン外のアカウントが入れませんか。**
入れません。ID トークンの `hd`（Google）/ `tid`（Microsoft）クレームで組織を検証します。

**Q21. 退職者を即座に遮断できますか。**
はい。管理者が無効化すると即時にログインできなくなり、
**SFU のトークンは5分で失効する**ため、最大5分で全アクセスが切れます。
SCIM による IdP 連動は Phase 4 以降の予定で、**現時点では未実装です**。

**Q22. 管理者は従業員の何を見られますか。**
**在席時間・稼働率・会話履歴は見られません。データも API も存在しません。**
見られるのは、メンバー一覧、ロール、監査ログ（[04](./04-audit-log.md)）、
そして**プロジェクト単位・匿名の「詰まり」件数**だけです。

これは制限ではなく製品の設計方針です（[00 原則3](../design/00-overview.md)）。
「稼働率を可視化したい」という要件がある場合、**本プロダクトは適していません。**

## 監査・ログ

**Q23. 監査ログは取れますか。**
はい。ログイン成功/失敗、管理操作、権限変更、エクスポート実行を記録します。
既定1年保持、CSV / JSON でエクスポートできます。仕様は [04](./04-audit-log.md)。

**一方で、従業員の利用行動（位置・会話・滞在時間）は記録しません。**
監査に必要なログはあり、監視に使えるログはない、という設計です。

**Q24. 会議の録画は残りますか。**
**録画機能がありません。** 文字起こしもありません。
「録画データの管理」という審査項目が発生しません。
なお、参加者が別ソフトで画面録画することは防げません（どの会議ツールでも同じです）。

**Q25. SOC 2 や ISO 27001 は取得していますか。**
**取得していません。** プロダクト自体がまだ実装段階です。

**Q26. 脆弱性診断やペネトレーションテストの結果はありますか。**
**ありません。** 実装前です。
Phase 1 以降で実施し、結果を本パッケージに追加する予定です。

## 答えに詰まったときの原則

この問答集に無い質問が来たら、**推測で答えない。**

1. 分かることは [設計ドキュメント](../design/) の該当箇所を示して答える
2. 未実装のことは「未実装です」と答える
3. 分からないことは「確認して回答します」と答え、**回答後に本文書に追記する**

**審査で信頼を失うのは、限界を隠したときである。**
「できません」と言った項目のほうが、あとで問題になりません。
