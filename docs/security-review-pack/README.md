# セキュリティ審査 提出パッケージ

情報システム部門のセキュリティ審査に提出するための資料一式。

> **⚠ これは設計段階の文書である。**
> プロダクトはまだ実装されていない。ここに書かれた内容は
> [設計ドキュメント](../design/) から導いた**予定**であり、実測・検証済みの事実ではない。
> 実際に提出できる状態になるのは、[06. ロードマップ](../design/06-roadmap.md) の
> Phase 1 完了後、記載内容を実装と突き合わせて検証したあとである。
> **現時点で顧客に提出してはいけない。**

## なぜこれを設計段階で書くのか

[02 壁4](../design/02-problem-solving.md) の通り、
**審査が長引く最大の原因は「聞かれてから調べる」こと**である。

聞かれる内容はおおむね決まっている。先に書いておけば、
審査期間が数ヶ月から数週間に縮む。そして書いてみると
**設計の穴が見つかる**（実際に見つかった。§「書いて分かったこと」を参照）。

## 2つの提出形態

本プロダクトは SaaS とセルフホストの両方で動く（[04 §10.1](../design/04-architecture.md)）。
**審査の内容が大きく変わる**ので、資料はどちらの形態かを明示して提出する。

| | SaaS | セルフホスト |
| --- | --- | --- |
| 通信先 | 提供側のドメイン数件 + 顧客の IdP | **顧客のネットワーク内で完結** |
| 音声の復号点 | 提供側の SFU（ただし E2EE 有効時は復号不可） | 顧客のサーバ |
| サブプロセッサ | あり（クラウド事業者） | **なし** |
| データの所在 | 提供側のリージョン | 顧客が決める |
| 審査の難度 | 標準的な SaaS 審査 | **大幅に軽い** |

**審査が厳しい顧客には、はじめからセルフホストを提案する。**
これは逃げではなく、[02 壁4 解3](../design/02-problem-solving.md) の設計方針である。

## 書いて分かったこと（設計の修正）

この資料を書く過程で、設計に2つの穴が見つかった。どちらも修正した。

### 1. Google Fonts が許可リストを2行増やしていた

[02 壁5](../design/02-problem-solving.md) で
「情シスが許可リストに追加する行数を5行以内に収める」と決めたのに、
Web フォントを `fonts.googleapis.com` と `fonts.gstatic.com` から読む設計になっていた。
**外部依存2件、かつセルフホストしても外に出る通信が残る。**

→ **フォントは自ホストに変更する**（[01 §4](./01-endpoints.md)）。
セルフホスト形態で「外部通信ゼロ」を名乗るための必須条件だった。

### 2. 「監査ログ1年」と「会話履歴を残さない」の整合を詰めていなかった

[00 原則3](../design/00-overview.md) は利用行動を残さないと言い、
[05 §7](../design/05-data-model.md) は監査ログを1年保持すると言う。
**では `PRIVATE_AREA_INVITED`（プライベートルームへの招待）は
1年残る「誰と誰が一緒にいた記録」ではないのか。**

→ 招待の記録は残すが、**招待先の部屋 ID と被招待者を残さない**形に変更した。
残すのは「誰がいつ招待操作を行ったか」だけ。
権限変更の追跡には足りるが、人間関係の復元には使えない（[04 §3](./04-audit-log.md)）。

**設計ドキュメントを読み返すだけでは、この2つは見つからなかった。**
「提出物として書く」という行為が検出器になった。
