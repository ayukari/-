# 10. 3D アセット仕様

**2026-09-13、3D を標準として採用することが決まった**（[06 O-8](./06-roadmap.md)）。

その結果、これまで「後で決める」で済んでいた**アセットの制作と配信が実装の律速**になる。
[06 リスク R-11](./06-roadmap.md)「3Dアセットの制作コストが想定を超える」は、
仕様が無いまま進めれば確実に顕在化する。この文書でそれを潰す。

> **前提の明示**: この決定は Phase 0 の実機ベンチ（内蔵GPU / VDI）**の前に**下された。
> 性能が足りるという確認は取れていない。したがって
> **「WebGL が無い / 遅い端末で確実に 2D へ落ちること」が必須条件**になる（§9）。

## 1. 予算 — 全体

[04 §4.6](./04-architecture.md) で決めた描画予算を、アセット側の制約に翻訳する。

| 項目 | 全体の上限 | 根拠 |
| --- | --- | --- |
| 初回ダウンロード | **5 MB 以内** | 業務PCの回線と、初回の離脱を防ぐため |
| テクスチャ総量（VRAM） | **64 MB 未満** | 内蔵GPU の共有メモリを圧迫しない |
| 三角形数（1フレーム） | **150,000 未満** | 30fps 維持 |
| ドローコール（1フレーム） | **100 未満** | ここが最も効く |

### 内訳の目安（1フロアあたり）

| 用途 | ダウンロード | 三角形 | ドローコール |
| --- | --- | --- | --- |
| アバター（全パーツ + 共通スケルトン） | 1.2 MB | 3,700 × 表示人数（最大25） | 25（+影1） |
| 部屋（床・壁・天井の庇・小口） | **0** | 12,000 | **3** |
| 家具・小物（29種） | **0** | 13,400 | **29**（種別ごとに1） |
| テクスチャ | **0** | — | — |
| **合計** | **1.2 MB** | **約 118,000**（25人時） | **約 58** |

**部屋のダウンロードが 0 になった**（[§5](#5-部屋--床壁家具)）。
家具を three 側でコードから組むので、glTF を1枚も落としてこない。
残るのはアバターだけで、5 MB の予算に対して 1.2 MB しか使っていない。

**ドローコールに 42 の余裕を残してある。** 新しいオブジェクト種別
（[08 Registry](./08-extensibility.md)）を足す余地である。
**これを使い切ったら、新規追加ではなくインスタンシングの見直しを先にやる。**

> 実測（2026-09-14、7人が居る部屋）: ドローコール **48〜51**、三角形 **48,000**。
> 部屋だけなら 25,354 三角形。

## 2. 形式とパイプライン

| 項目 | 採用 | 理由 |
| --- | --- | --- |
| モデル形式 | **glTF 2.0（`.glb`）** | Web 標準。Three.js が標準で読める |
| 圧縮 | **glTF 標準の量子化のみ**（`KHR_mesh_quantization`）。Draco / Meshopt は使わない | 量子化は three.js の GLTFLoader が**追加のデコーダ無し**で読める。Draco も Meshopt もデコーダ（数百KB）の配信が増え、削れる量より不利になる。家具が増えて 3MB を超えたら再検討する |
| 後処理 | **[glTF Transform](https://gltf-transform.dev/)**（`assets/optimize.mjs`）。dedup → prune → resample → weld → quantize | Blender のエクスポータは素直に書き出すので、そのままだと無駄が多い。**1,215 KB → 694 KB（43%減）** |
| テクスチャ | **1枚も使わない**（アバターも部屋も頂点カラー） | 色数が少なく、頂点カラーで足りた。テクスチャが0なら VRAM も初回DLも増えず、着せ替えもテクスチャ差し替え無しでできる。部屋の陰も頂点カラーに焼いてある（[§5](#5-部屋--床壁家具)） |
| GPU圧縮テクスチャ（KTX2 / Basis） | **v1 では使わない** | デコーダの追加配信が要り、初回 5MB を圧迫する。テクスチャ総量が 64MB に収まる限り不要 |
| マテリアル | アバターは **`MeshToonMaterial`**、建材・家具は **`MeshLambertMaterial`**（PBR を使わない） | どちらも内蔵GPU で軽い。トゥーンは4段の小さなグラデーションマップ1枚だけで、ポストエフェクトを足さずにアニメ寄りの陰影になる |
| ライティング | **頂点カラーに事前ベイク**（ライトマップ用のUVも持たない） | 動的ライトを使わない（[02 §6.3](./02-problem-solving.md)） |
| 影 | **ブロブシャドウ** ✅ 実装済み。全員ぶんを1つの `InstancedMesh` に畳んで **1ドローコール** | 動的シャドウを使わない。足元に丸い影が無いと人が浮いて見える |
| ライティング | **3灯**（キー=暖色の平行光 / フィル=半球光・下は木の床色 / リム=後ろから寒色） | 影を焼かないぶん、光の当て方だけで立体を出す。リムが背景から輪郭を分ける |
| 焼き込みの陰 | **頂点カラーのアルファに「部位ID + 明るさ」を同居させる** | データが1バイトも増えずに、のっぺりした低ポリに奥行きが出る |
| アニメーション | glTF 内のクリップ | 後述 §4 |

### 配信

- すべて**自ホスト**。CDN も外部アセットサービスも使わない
  （[審査パッケージ 01 §4](../security-review-pack/01-endpoints.md)）
- 長期キャッシュ（内容ハッシュ付きのファイル名 + `immutable`）
- **業務データはキャッシュしない。キャッシュするのはアセットだけ**

## 3. 作風（O-9 への回答）

| 項目 | 決定 |
| --- | --- |
| 全体 | **low-poly / フラットシェーディング寄り。** 陰影はベイク、輪郭線なし |
| 色 | [00](./00-overview.md) の「室内に差す午後の光」。彩度を抑えた木・布・金属の3系統 + アクセント |
| ディテール | **固定カメラ（クォータービュー）なので、カメラから見えない面は作らない** |
| 縮尺 | **1 タイル = 1 ユニット = 実寸 約 1.0 m** |
| 人の背丈 | 約 1.6 ユニット（アバターの `ht` 係数で ±12%） |

> **固定カメラであることがアセット制作コストを直接下げている。**
> 自由回転カメラなら全方位のディテールが要る。
> [02 §6.7](./02-problem-solving.md) でカメラを固定した判断が、性能だけでなく
> **制作費にも効いている**。

| 項目 | 上限・決定 | 実測（2026-09-13） |
| --- | --- | --- |

| パーツ数 | — | **83**（素体3・髪14・トップス30・ボトムス24・靴5・小物7） |
| 三角形数 | 1体 1,200 → 1,400 → 1,900 → **3,700 以下に再改定**（下記） | 最重の組合せ 3,636 / 平均 約 3,270 |
| ボーン数 | **18 以下**（腰・背・首・頭・肩肘手 ×2・股膝足 ×2） | 18 |

| マテリアル | 1体 2つまで → **1つ**（頂点カラー1本で肌も服も塗る） | **1体1ドローコール** |

| 表情・口パク | **作らない**（音声と同期させる仕組みを持たないため嘘になる） | — |

### パーツを組み合わせる方式にした（2026-09-13）

当初は「3体型 × 6色 = 18通りのプリセット」だった。
[01 §3b](./01-market-research.md) で **gogh** を調べた結果、
**アバターの作り込みそのものが継続利用の理由になっている**ことが分かったので、
パーツの組み合わせに切り替えた。

| | |
| --- | --- |
| 素体 | 3（体型・細め/ふつう/丸め） |
| 髪 | 14（ショート・分け目・ボブ・ロング・ポニー・ツイン・お団子・三つ編み・ツンツン・ウェーブ・刈り上げ・くるくる・ハーフ・サイド） |
| トップス | 10（T・長袖・タンク・パーカー・シャツ・セーター・カーデ・ワンピ・ジャケット・ベスト）× 体型3 |
| ボトムス | 8（パンツ・ショート・クロップ・ワイド・レギンス・スカート・ロングスカート・カーゴ）× 体型3 |
| 靴 | 5（スニーカー・ローファー・ブーツ・サンダル・ハイカット） |
| 小物 | 7 + なし（めがね・ヘッドホン・キャップ・ニット帽・リボン・マフラー・ヘアピン） |
| 配色 | 肌8・髪14・ボトムス10・靴6・小物10・瞳6（服の色は名簿の色＝その人の色） |

**種類を増やしてもドローコールは増えない。**
クライアントが、選んだパーツを**1つのジオメトリに統合してから描く**ため
（`client/src/avatar.js`）。1人 = 1ドローコールは変わらない。

### 三角形の上限を 1,900 → 3,700 に上げた（2026-09-14）

**上げた理由は「かくかくで初心者が作った感がある」という指摘。**
原因は2つあり、どちらも三角形を食う直し方しか無かった。

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| 手足の関節に角が立つ | 腕＝円錐＋球＋円錐＋球、と**継ぎ足して**いた。継ぎ目は必ず折れる | 肩→肘→手首を**1本の掃引面**にした（`limb2`）。骨は高さで2本をブレンドする（`bind_split`） |
| 全体が多面体に見える | フラットシェーディングで、球だけが滑らかだった | `shade_smooth_by_angle(38°)` を全パーツにかけた。角は角のまま残り、曲面だけ滑らかになる |

**上げてよい根拠は人数側にある。** `server/test/assets.test.js` が
`3,700 × 25人 + 部屋 31,000 = 123,500 < 150,000`（[§1](#1-予算--全体)）を
テストとして持っている。部屋の実測は 25,354 なので、見積りにはさらに余裕がある。

**ファイルは4つに分けてある。**

| ファイル | 中身 | なぜ分けるか |
| --- | --- | --- |
| `avatar-common.glb` | 骨・3クリップ・髪14・靴5・小物7 | 体型に依らないので1回だけ配ればよい |
| `avatar-body-{0,1,2}.glb` | 素体・トップス10・ボトムス8 | 体型ごとに太さが違うので分かれる。**動きは持たない** |

1ファイルに全部入れると、同じ髪が3回ダウンロードされ、動きも3重になる。
分けたことで 1,786 KB → **1,216 KB**。

> ⚠ **骨の並びが4ファイルで同じでなければならない。**
> クライアントは体型ファイルのジオメトリを共通ファイルの骨に結びつけるので、
> 並びが違うと手足が飛ぶ。`server/test/assets.test.js` が検査している。

### 三角形の上限を 1,200 → 1,900 に改定した（2026-09-13）

1,200 は**モデルが1体も無い段階で置いた数字**である。実際に作ると 1,244 で、
そこにパーツ（帽子・マフラー・スカート）を足すと最重の組み合わせで 1,868 になった。

削れる場所は残っていたが、削ると目・前髪・ほおのどれかを落とすことになる。
この形は**固定の斜め見下ろしで顔が読めること**が要件なので、そこを削ると作る意味が減る。

一方で、この数字が縛っている本当の上限は
**1フレーム 150,000三角形**（[§1](#1-予算--全体)）のほうである。

| | 1,200 のとき | **3,700 のとき（最悪）** |
| --- | --- | --- |
| 25人ぶん | 30,000 | **92,500** |
| 部屋（§1の内訳。実測 25,354） | 31,000 | 31,000 |
| 合計 | 61,000 | **123,500**（上限の 82%） |

**全員が最も重い組み合わせを選んでも上限に収まる。**
ただし 82% まで来たので、**ここから先はアバターを重くする余地が無い**。
次にパーツを足すときは、足したぶんだけどこかを削ること。

`server/test/assets.test.js` が、1体の上限と**25人ぶんの合計**の両方を見張っている。

### どう作っているか

**[../../assets/avatar.blend.py](../../assets/avatar.blend.py) で手続き的に生成し、
[../../assets/optimize.mjs](../../assets/optimize.mjs) で縮めている。**

```bash
cd assets && npm run build        # Blender で生成 → glTF Transform で最適化
```

### 何が容量を食っていたか（2026-09-13 実測）

```
WEIGHTS_0 77KB   POSITION 58KB   NORMAL 58KB   COLOR_0 39KB   indices 27KB
```

**`WEIGHTS_0` が最大だった。** うちのスキニングは剛体（どの頂点も重みは 1,0,0,0）なのに、
`float32 × 4 = 16バイト/頂点` を使っていた。8bit で足りる。
法線と色も 8bit で足りる。これだけで **43%** 落ちた。

> ⚠ **位置は量子化しない。**
> 位置を量子化すると、その分を打ち消す変換が**逆バインド行列**に入る。
> うちは4ファイルのジオメトリを1つの骨に結びつけて統合するので、
> ファイルごとに違う逆バインド行列が入ると手足がずれる。
> さらに既定の「メッシュごとに範囲を決める」設定だと、**skin が 1 → 26 に分裂**する。

- 寸法規約（[§5](#5-部屋--床壁家具)）を人手で守らせない。スクリプトが定数として持っている
- 三角形数と最重の組み合わせを出力するので、予算を見ながら形を決められる
- **ライセンスの出所が問題にならない**（[§6](#6-調達)の商用可・改変可・再配布可を自前で満たす）
- **83パーツを手でモデリングしない。** 髪も服も引数の違いで、追加は表に1行足すだけ

確認は **[/avatar-gallery.html](../../client/avatar-gallery.html)**（100体を一度に並べる・
部位ごとの一覧）と **[/avatar-preview.html](../../client/avatar-preview.html)**（1体を回して見る）で行う。

**頂点カラーのアルファに「部位ID」と「焼き込みの陰」を同居させてある。**

```
アルファ × 16 → 整数部 = 部位ID、小数部 = 明るさ（0=暗い 1=明るい）
```

クライアント（`client/src/avatar.js`）はこれを見て、人ごとに肌・髪・服・ズボン・靴を塗り替え、
同時に陰を掛ける。テクスチャを差し替えないので、何人いてもマテリアルは1つのままでいられる。

陰は「体の下にあるほど暗い」という1本の勾配だけ。
最初はパーツごとに勾配を引いたが、**肘・肩・裾の境目で明るさが飛んで段ができた**
（腕に輪が入った）。体の全高で1本引けば連続する。

> ⚠ glTF エクスポータは、マテリアルがアルファを使っていないと COLOR_0 を VEC3 に落とす。
> 落ちると部位IDが消え、**全員が同じ色で立つ**。一度これを踏んだので、
> `assets.test.js` が VEC4 であることと部位IDが揃っていることを検査している。

### 外部アバターサービスを使わない

VRM、Ready Player Me などの**外部アバターサービスに依存しない**。

- セルフホスト形態で「外部通信は認証だけ」と言えなくなる（[02 壁4](./02-problem-solving.md)）
- アバターの見た目が外部サービスの都合で変わる
- 利用者の外部アカウントとの紐付けが発生する

**プリセット固定という判断が、ここでも効いている。**

## 5. 部屋 — 床・壁・家具

### 家具は **three 側でコードから組む**（glTF を落としてこない）

`client/src/props.js`。机も棚もソファも、箱と円柱の組み合わせで足りる形なので、
**コードで組めばダウンロードは1バイトも増えない**。形を直すのも速い。
骨と動きを持つアバターだけが glTF を要る。

| | 2026-09-14 の実測 |
| --- | --- |
| 家具の種類 | **29**（机・椅子・モニタ・ノートPC・マグ・観葉植物2・棚・ソファ・ローテーブル・ラグ2・フロアランプ・ペンダント・収納・間仕切り・窓・ポスター・時計・ホワイトボード・掲示板・貼り紙・案内・席・給湯カウンター・ウォーターサーバー・コート掛け・ビーズクッション・座布団・積んだ本・木箱） |
| 部屋の三角形（床・壁・天井・家具すべて） | **25,354** |
| ドローコール | **種別ごとに1**（`InstancedMesh`）。合計 48〜51 |
| ダウンロード | **0 バイト** |

### 寸法規約

**すべてグリッドに載せる。** 論理は 1 タイル単位なので、見た目もそれに合わせる。

| 種類 | 寸法 |
| --- | --- |
| 床タイル | 1 × 1 |
| 壁 | 厚み 1.0（1タイル）、高さ 2.90 |
| 机 | 高さ 0.72、平面は占有タイル × 0.93 |
| 棚・什器 | 高さ 0.80〜1.50 |
| 椅子（座面） | 高さ 0.42 |

**グリッドに載らない寸法のアセットは受け入れない。**
当たり判定がタイル単位（[09](./09-protocol.md)）なので、見た目と判定がずれる。

### 壁は「置いた家具」と同じく **blocked から生える**

外周のタイルを `blocked` に入れる（`server/src/world.js`）と、
クライアントはそれを見て壁を建てる。手で壁の絵を並べると、表現と論理がずれる。

> **実際に外した。** 外周を `blocked` に入れ忘れていたので、
> 壁に付くもの（窓・時計・ホワイトボード）が**何も無いところに浮いていた**。
> 誰も気づかないまま数日動いていた。

### 手前は立てない — 切り取った模型にする

見下ろしのカメラで全周に壁を立てると、**手前の壁で部屋の中が見えない**。

| 位置 | 高さ |
| --- | --- |
| 奥の壁（z = 0） | 2.90 |
| 左右の壁（奥 〜 H-8） | 2.90 |
| 左右の壁（H-7 〜 H-4） | 1.42 |
| 左右の壁（H-3 より手前）・手前の壁 | **建てない** |

手前を切り落とすと床が紙一枚に見えるので、床の外周に**小口**（厚み 0.22）を回す。
奥の壁の**裏側にだけ**天井の庇を伸ばす（`buildCeiling`）。
庇は部屋の上には出さない。出すと見下ろしのカメラから中身が全部隠れる。

### 陰は頂点カラーに焼く

動的な影を使わない（[02 §6.3](./02-problem-solving.md)）代わりに、3つを焼く。

| 焼くもの | どこに |
| --- | --- |
| 「低いところほど暗い」 | 家具・壁・小口 |
| 「通れないタイルの際ほど暗い」 | 床（家具の足元が締まる） |
| **窓から差す日なた** | 床。窓の位置から手前へ、斜めに伸びる帯 |

日なたが効く。部屋全部が同じ明るさだと、どれだけ家具を置いても書き割りに見える。

> **`y ** 0.55` に負の数を入れてはいけない。**
> 頂点は float32 なので、床に接する面の y が `-7e-10` のような微小な負になる。
> 負の冪乗は `NaN` になり、`NaN` の頂点カラーは**真っ黒**に描かれる。
> 壁が全部黒くなって、原因を掴むのに時間がかかった。`clamp01()` を必ず通すこと。

### インスタンシング

**同じ形は1回のドローコールで描く。**

- 床、壁、机、椅子、棚は `InstancedMesh` を前提に作る
- したがって**同じ種類の家具は同じジオメトリでなければならない**
- 「似ているが微妙に違う机」を増やすと、ドローコールが種類数だけ増える

> **家具のバリエーションを増やすことは、そのままドローコール予算を食う。**
> 変化をつけたいときは、ジオメトリではなく**配置と色**で出す。

### カメラは「部屋が収まる距離」を毎フレーム計算する

数字を手で決めない（`client/src/render3d.js`）。

```
俯角は 56° 固定
距離 = min( 部屋の幅が画角に収まる距離, 部屋の奥行きが画面を埋める距離 )
```

- **幅だけを見て引くと**、縦持ちで画面の下半分が部屋の外になる
- **奥行きだけを見て寄ると**、横持ちで部屋の左右が切れる
- 横持ちでは部屋がほぼ丸ごと入るので、視点はほとんど動かない（箱庭の見え方）

> **部屋を 24×16 から 20×14 に縮めた。** 24×16 は「広い床」であって部屋ではなく、
> どの画角でも壁が1枚も見えなかった。ひと目で見渡せることのほうが、広さより効く。

## 6. 調達

| 方法 | 扱い |
| --- | --- |
| **既製の low-poly アセットパック** | **起点にする。** ライセンス条件を満たすものだけ |
| 自作 | 足りない分（ドア、貼り紙、ボードなど固有のもの） |
| 生成AI による 3D 生成 | v1 では使わない。ライセンスと品質が読めない |

### ライセンスの受け入れ条件

次をすべて満たすものだけを使う。

- [ ] **商用利用が可能**
- [ ] **改変が可能**（寸法規約に合わせるため必須）
- [ ] **再配布が可能**（セルフホスト構成で顧客のサーバに置かれるため必須）
- [ ] クレジット表記の要否を確認済み（必要なら設定画面にクレジット欄を設ける）
- [ ] ライセンス文書をリポジトリに含めた

**再配布可が最も見落とされやすい。**
セルフホストを主要な導入形態にしている以上、アセットは顧客のサーバにコピーされる。
「再配布不可」のアセットは使えない。

## 7. ロード戦略

```
起動時         アバターのパーツ 4ファイルのみ（694 KB）
               → これだけで全員が描ける
チーム選択時   何もロードしない
部屋に入る時   **何もロードしない。** 床・壁・家具はコードから組む（[§5](#5-部屋--床壁家具)）
               → フロア定義（JSON、数 KB）だけを HTTP で取る
フロア移動時   同上。追加のダウンロードは発生しない
```

- **ロード中に待たせない。** [08 の縮退](./08-extensibility.md) を使い、
  2D ビューで先に部屋に入れてから 3D に差し替える
- **ロードに失敗したら 2D ビューのまま続行する。** エラーで止めない
- **アバターのモデルが届くまでは簡易表示（カプセル）で動かす。**
  読み込みに失敗してもそのまま遊べる（`client/src/render3d.js`）

## 8. アセットの受け入れ基準

新しいアセットを追加するときのチェックリスト。

- [ ] `.glb`（Draco 圧縮済み）
- [ ] 寸法規約（§5）に載っている
- [ ] 三角形数が種別の目安以内
- [ ] マテリアルが2つ以下、`MeshLambertMaterial` で破綻しない
- [ ] ライトマップがベイク済み、動的ライトを要求しない
- [ ] カメラから見えない面を持っていない
- [ ] 追加後も**全体のドローコール100未満・三角形150k未満**を保つ（実測）
- [ ] ライセンス条件（§6）を満たし、ライセンス文書を含めた
- [ ] **2D ビューでの描画（`draw2d`）も実装した**（[08 Registry](./08-extensibility.md)）

**最後の項目を飛ばすと、3D でしか見えないオブジェクトができる。**
それは縮退経路を壊すということであり、§9 に反する。

## 9. 必須条件 — 3D を採用しても 3D を必須にしない

**この節が、3D 採用の前提条件である。**

| 条件 | 実装状況 |
| --- | --- |
| WebGL が使えない端末で、**2D ビューで自動起動する** | ✅ プロトタイプ・実クライアントの両方に実装（`--disable-3d-apis` で確認） |
| そのとき 3D ボタンを無効にし、理由を表示する | ✅ 同上 |
| アバター作成画面も WebGL 無しで動く | ✅ 2D プレビューを実装 |
| 3D のロードに失敗しても 2D で続行する | ✅ アバターのモデルが落ちても簡易表示のまま止まらない。WebGL 自体が無ければ 2D で起動する |
| フレームタイムが閾値を割ったら軽量モードを提案する | ⬜ Phase 2 |
| すべてのオブジェクト種別が `draw2d` と `listRow` を持つ | ✅ 現状すべて実装済み。§8 のチェックリストで維持する |

**3D が動かない端末が1台でもある限り、この表が全部 ✅ でなければ 3D を出荷しない。**
