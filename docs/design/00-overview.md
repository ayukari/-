# 00. コンセプトとスコープ

> 仮称: **Hidamari（ひだまり）** — プロダクト名は未確定のプレースホルダです。
>
> **前提**: このカテゴリには既に複数の競合が存在する。本ドキュメントを読む前に
> [01. 既存プロダクト調査](./01-market-research.md) を参照すること。
> 以下の内容は「既存が解けていない部分に賭ける」という前提で書かれている。
>
> また、このプロダクトが越えるべき壁は [02. 問題解決](./02-problem-solving.md) に6つ整理してある。
> 定着しない壁（1〜3）と、**そもそも導入されない壁（4〜6: セキュリティ審査・企業ネットワーク・業務PCの性能）**である。

## 1. 一言でいうと

**会社単位で「そこに居る」感覚を持てる、急かさないバーチャルオフィス。**

Gather (gather.town) のようなアバターで歩き回れるオフィス空間に、
Zoom 相当のビデオ会議とプライベート会議室、そしてチームのタスク管理を統合する。

Gather や Zoom との差分は「機能の多さ」ではなく **設計思想** に置く。
既存ツールが「常時つながっている＝生産的」を前提にしているのに対し、
本プロダクトは **つながらない自由を UI レベルで保証する**。

## 2. なぜ作るのか（課題）

リモート/ハイブリッド勤務のチームには、次の3つが同時に起きている。

| 課題 | 具体的な症状 | 既存ツールの状況 |
| --- | --- | --- |
| **雑談の消滅** | 「ちょっといいですか」が Slack DM の重さになり、質問が滞留する | Slack は非同期前提。Zoom は「会議を設定する」重さがある |
| **文脈の分散** | タスクは Jira、会話は Slack、会議は Zoom、資料は Drive。どれが今の話か分からない | ツール間にリンクはあるが「同じ場所にいる」感覚がない |
| **常時監視の圧** | 在席ステータス、既読、レスポンス速度が暗黙の評価指標になる | プレゼンス機能が「監視」として機能してしまっている |

3つ目が本質的に重要である。1と2だけを解こうとすると
「常時マイクON・常時カメラON のバーチャルオフィス」になり、
導入したチームの多くが数週間で使わなくなる。
**Chill であること＝低圧であること** を機能要件と同格の制約として扱う。

## 3. ターゲット

- **第一想定**: 10〜80名程度の単一企業（1ドメインの Google Workspace / Microsoft 365 を持つ規模）
- リモート/ハイブリッドで、職能横断のチームが3〜10個ある組織
- 「全員が同じフロアにいた頃のテンポ」を取り戻したいが、監視ツールは入れたくない

**非ターゲット（当面）**:
- 数千人規模のエンタープライズ（SSO/SCIM/監査要件が重い）
- 社外ゲストを大量に招くイベント会場用途（Gather の得意領域、ここでは競合しない）
- コンシューマ向けのメタバース/ゲーム用途

## 4. Chill 設計原則

以降のすべての設計判断は、この5原則に照らして決める。
機能要件と衝突した場合、**原則が優先する**。

### 原則1: 近づくことは通話の開始ではない

Gather 型の「近接すると自動で音声が繋がる」は、
初対面や上司が近くにいる状況で強い緊張を生む。

本プロダクトでは近接は**可聴可能性の提示**までとし、実際の接続は明示的な行為で開く。

- 近づく → 相手のアバターに「話しかけられる」インジケータが出るだけ
- 話す → **座る（テーブルに着席）** または **ノックして応答を得る** の2択
- 例外: 「オープン」ステータスの人同士は自動接続してよい（本人が事前に許可している）

### 原則2: ステータスは自己申告のみ。推定しない

- キーボード入力の有無、マウス移動、アプリのフォーカスからステータスを**推定しない**
- ステータスは `オープン / 集中中 / 会議中 / 離席` の4つのみ。本人だけが変更できる
- 「集中中」の人は近接しても通話対象にならず、通知も溜まるだけで飛ばない

### 原則3: 在席ログを管理者が見られない

- 誰がいつ何時間ログインしていたかの**時系列ログを保持しない**（現在の状態のみ Redis に持つ）
- 管理者向けの「稼働率」「オンライン時間」ダッシュボードを**作らない**
- 集計するのは組織全体の匿名指標のみ（例: 同時接続数の推移）

これは技術的制約ではなくプロダクト上の約束であり、
[05. データモデル](./05-data-model.md) でスキーマとして担保する。

### 原則4: タスクは急かさない

- 期限切れタスクを赤くしない、バッジで数を出さない、通知で追わない
- 表示するのは「今週やること」と「詰まっていること」だけ
- ベロシティ、消化率、個人別完了数のグラフを**作らない**
- 締切は `dueDate`（合意された期日）と `focusWeek`（今週やるつもり）を分け、後者を主役にする

### 原則5: プライベートは物理的に保証する

- プライベートルームの音声・映像は、外部の参加者に**そもそも配信されない**（UIで隠すのではなく、SFU のサブスクリプション自体を張らない）
- 入室は招待制 or ノック承認制
- 「誰が今どの個室にいるか」は、その個室のメンバー以外には非公開にできる

## 5. スコープ

### やること（v1 の範囲）

1. 会社ドメイン単位の認証・組織管理
2. タイルマップ上のアバター移動とプレゼンス
3. 近接ベースの音声通話（原則1に従った opt-in 接続）
4. 会議室（オープン/プライベート）とビデオ・画面共有
5. プロジェクト/タスクのボード管理と、空間との連動
6. チャンネル/DM のテキストチャット

### やらないこと（明示的な非スコープ）

| 項目 | 理由 |
| --- | --- |
| アバターのカスタマイズ課金、装飾アイテム | Chill の本質ではない。v1 では固定プリセットのみ |
| フロアエディタ（社内の誰でも作れる） | 運用が荒れる。v1 は JSON 定義を管理者が入れる形 |
| 録画・自動議事録 | 原則3と緊張する。やるなら参加者全員の明示同意 UI を先に設計する |
| ネイティブアプリ | ブラウザ（WebRTC）で足りる。インストール不要であることがセキュリティ審査で効く（[02 壁4](./02-problem-solving.md)） |
| 3D 空間 | 業務PC・VDI で動かない。2D タイルマップ固定（[02 壁6](./02-problem-solving.md)） |
| Slack / Jira との双方向同期 | 「文脈の分散」を解く目的に反する。エクスポートのみ提供 |
| モバイル完全対応 | v1 はテキスト/タスク閲覧のみのレスポンシブ。空間はデスクトップ前提 |

## 6. 成功の判断基準

導入から8週間後に、以下が観測できていれば方向性は正しい。

- **継続率**: 週3日以上ログインする人が、導入時メンバーの60%以上
- **雑談の発生**: 会議室外（オープンエリア）での通話が、全通話セッションの30%以上
- **重さの解消**: 通話の中央値が10分未満（＝「ちょっといい？」が成立している）
- **反証指標**: 「集中中」ステータスの利用率が5%未満なら、原則2が機能していない（心理的に使いづらい）
