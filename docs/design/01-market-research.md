# 01. 既存プロダクト調査（2026年9月時点）

「会社単位で Chill できる、Gather 的な空間 + オンライン会議 + プライベート会議室 + タスク管理」
というアイデアが既に実在するかを調べた。

## 結論（先に）

1. **空間 + 会議 + 個室**の部分は **完全に実在する**。しかも6社以上が競合している成熟カテゴリ。
2. ただし **「タスク管理まで統合したもの」は見当たらない**。ここは空白。
3. 一方でこのカテゴリは **2022年をピークに淘汰局面**に入っている。撤退・停滞したプロダクトが複数ある。
4. したがって「誰も作っていないから作る」ではなく、**「なぜ誰も作らなかったのか」に答えを持つこと**が先。

## 4. アイデアとの照合

ユーザーが挙げた要素を1つずつ既存プロダクトに当ててみる。

| やりたいこと | 実在するか | どこにあるか |
| --- | --- | --- |
| アバターで歩き回る社内空間 | ✅ 完全に実在 | Gather, ovice, WorkAdventure, SoWork |
| 近づくと話しかけられる（近接音声） | ✅ 完全に実在 | 同上 |
| オンライン会議（Zoomの代替） | ✅ 完全に実在 | 全社。画面共有・ホワイトボードまで込み |
| プライベートな個室・会議室 | ✅ 完全に実在 | 全社。Roam は特にここが主役 |
| テキスト連絡・チャット | ✅ 実在 | 全社（ただし Slack ほど作り込まれていない） |
| **タスク管理との統合** | ❌ **ほぼ無い** | Roam の比較資料でも「どのプラットフォームにも組み込みのタスク/プロジェクト管理は無い」とされる。SoWork が唯一持つが軽量で、外部ツール併用が前提 |
| **「Chill＝低圧」を設計思想として掲げる** | ❌ 見当たらない | むしろ逆で、各社「プレゼンス可視化」「稼働分析」「AIによる自動記録」を売りにしている |

**空白は2箇所ある**: ①タスク管理の統合、②低圧・非監視という設計思想。

---

## 5. 空白が空白のままである理由（正直な検討）

「誰もやっていない」は、多くの場合「やったが失敗した」か「やる価値が無かった」のどちらかである。
ここを飛ばすと同じ穴に落ちるので、仮説を立てておく。

### 理由1: 乗り換えコストが非対称

バーチャルオフィスは「Zoom より気軽」で入れられる。既存の会議習慣を壊さないから。
一方タスク管理は **Jira / Asana / Linear / Notion / Backlog に既にデータと運用が乗っている**。
新しい空間ツールにタスクを移させるのは、会議を移させるより桁違いに重い。
だから各社は統合ではなく**連携**（Slack / Zapier / Calendar）に逃げている。

> これは本プロダクトにとって最大のリスク。「タスク管理も付いています」では誰も移らない。
> 移るとしたら「**空間にいるからこそ成立するタスクの見え方**」がある場合だけ。
> 例: 誰かの席に近づくと、その人が今週やると言っているものが見える。会議室に入ると、その会議のタスクが自動で出ている。
> つまり **タスクを空間の関数にする** ところまでやらないと、統合する意味がない。

### 理由2: 定着率がこのカテゴリの共通課題

無料プランを廃止した Gather、停滞した Kumospace、撤退した NeWork と Tandem。
これらが示すのは「面白いが、数週間で開かなくなる」という共通のパターン。
Roam が空間移動を捨てて部屋型に寄せ、SoWork が AI議事録に寄せているのは、
どちらも「歩き回る楽しさ」だけでは維持できないと判断した結果と読める。

> 逆に言うと、**毎日開く理由**を空間の外に持つ必要がある。
> タスク管理はその候補として筋が良い（毎日開く）。この点ではアイデアの方向性は正しい。

### 理由3: 「監視されている感」は解決策が売りにくい

「稼働ログを取りません」「分析ダッシュボードを作りません」は、
**導入を決裁する管理者にとっては機能の欠如**に見える。
使う側には刺さるが、買う側には刺さらない。ここが売りにくい理由。

> 10〜80名の、経営者＝使う人でもある規模ならこの矛盾は起きにくい。
> [00-overview.md](./00-overview.md) のターゲット設定はこの点で妥当。

## 6. 現実的な選択肢

調査を踏まえた、この先の進み方の候補。

### A. 自社/身内向けに作る（学習と実用の両立）

- 既存プロダクトと勝負しない。自分たちのチームが使うものを作る
- **WorkAdventure (OSS) をセルフホスト**すれば、空間 + 近接音声 + 会議室は数日で手に入る
- その上に「タスク管理」と「Chill 原則」を自分たちで足す
- 最短で「実際に使えるもの」に到達でき、ゼロから WebRTC を組む必要がない

### B. ゼロから作る（差別化を最大化） ← **2026-09-13、これに決定**

- 空間からタスクまで一貫して設計できる。理由1で書いた「タスクを空間の関数にする」を本気でやれる
- ただし **WebRTC / SFU の運用が重い**（WorkAdventure ですら LiveKit + Coturn で公開IPのサーバ2台を要求する構成）
- 学習目的としては最良。事業目的としては、上記の定着率リスクを正面から受ける

### C. 逆張り: タスク管理を主、空間を従にする

- 「Linear に居場所が付いたもの」。まずタスクツールとして毎日開かれ、そこに同僚の気配と会話が乗る
- 乗り換えコストの問題は残るが、少なくとも「空間ツールとして飽きる」問題は回避できる
- 既存プレイヤーが誰も取っていないポジション

---

> **決定（2026-09-13）: B（ゼロから作る）。**
> 3D を標準として採用したことで、**2D タイルマップ前提の WorkAdventure をベースにする利点が大きく減った**
> （描画層をまるごと差し替えることになる）。
> ただし A の調査価値は残るので、[06 Phase 0](./06-roadmap.md) の 0-2（セルフホストの実測）は
> 「作るコストの比較対象」として残している。

## 7. 推奨する次の一手

1. **Gather と ovice を実際に1〜2週間使う。** 特に「何日目に開かなくなるか」を観測する。この体験が無いまま設計すると、既存プロダクトが解けなかった問題を再発明することになる
2. 並行して **WorkAdventure をセルフホスト**して構成を確認する。作るコストの実測になる
3. その上で、選択肢 A / B / C を選び直す

なお、**プロトタイプを作ること自体の価値は調査結果とは独立して高い**。
「実在するからやめる」ではなく、「実在するから、どこで違うものにするかを決めてから作る」が妥当な結論。
