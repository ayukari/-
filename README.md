# Hidamari（仮称）

**会社単位で「そこに居る」感覚を持てる、急かさないバーチャルオフィス。**

アバターで歩き回れる **3D の社内空間**に、オンライン会議・プライベート会議室・
そして「今週やること」の共有を統合する。
（3D は採用するが**必須にはしない** — 非力な端末では 2D ビューやリスト表示に縮退する）

現在は **設計フェーズ**。実装コードはまだありません。

---

## これは何か

Gather や ovice のようなバーチャルオフィスに近い見た目をしているが、目指しているものが違う。

既存ツールが「常時つながっている＝生産的」を前提にしているのに対し、
このプロダクトは **つながらない自由を UI とデータモデルのレベルで保証する**。

| このプロダクトが**しない**こと | 理由 |
| --- | --- |
| 近づいたら自動で通話を始める | 初対面や上司が近くにいる状況で緊張を生む |
| 入力状況からステータスを推定する | ステータスは本人だけが決める |
| 個人の在席時間・稼働率を記録する | **データもAPIも存在しない**（管理者にも見えない） |
| 期限切れタスクを赤くする・件数を通知する | 急かさない |
| 通話を録画する・文字起こしする | 上記と衝突する。情報漏洩リスクも減る |
| 3D を必須にする | 業務PC・VDI で動かない端末がある。2D ビューへ縮退できる形にする |
| カメラを自由回転させる / 影・ポストエフェクトを使う | 3D酔いと、内蔵GPU で 30fps を割る主因 |
| ネイティブアプリを配る | インストール不要のほうが導入できる |

「設定でオフにできます」ではなく「**そもそも保存していません**」を選んでいる。

## 中核にあるもの: フォーカスカード

このプロダクトが持つタスクデータは、原則として **「今週やると本人が宣言した3〜5件」だけ**。

```
┌─ フォーカスカード（山田 / 2026-W37）──────────┐
│ ◻ 決済APIのリトライ設計を書く      → PROJ-412  │
│ ◻ 新人のオンボード資料を1章だけ                │
│ ◻ 請求バッチの原因調査（詰まってる）  ⚠ 3日    │
└────────────────────────────────────────────────┘
```

- Jira / Linear / Notion を置き換えない。**同期もしない**。上に薄い層を1枚だけ載せる
- 移行コストは実質ゼロ（月曜の朝に3行書くだけ）
- **アバターに近づくと、その人のカードが見える** → 「今なにやってるんですか?」を聞かずに済む
- 3日以上動いていない項目は、**個人ではなくプロジェクト単位**で「詰まり」として表示される

空間はフォーカスカードを面白くする装置であって、逆ではない。
だから **空間を捨てても（リストモード）、通話を捨てても（テキストモード）、このプロダクトは成立する。**

## 3D について

見た目は 3D（low-poly の斜め見下ろし）にする。ただし **3D を必須にはしない。**

**論理レイヤー（2Dグリッド座標・当たり判定・エリア）と表現レイヤー（3D描画）を分離**してあるので、
同じ空間を 3D / 2D / リスト表示のどれでも描ける。位置同期も帯域も 3D 化の影響を受けない。

```
3D 標準 → 解像度スケーリング(0.5x) → 3D低品質 → 2Dビュー → リストモード
                                                    ▲ WebGL不可・VDI    ▲ 極端に非力
```

内蔵GPU で 30fps を守るための制約: **影なし・動的ライトなし・ポストエフェクトなし・固定カメラ・
ドローコール100未満・初回DL 5MB以内**。3D が重くなる主因はポリゴン数ではないので、ここを外さなければ動く。

最終判断は Phase 0 の実機ベンチで行う（[02 §6](./docs/design/02-problem-solving.md)）。

## 越えるべき6つの壁

| # | 壁 | 一言でいう解 |
| --- | --- | --- |
| 1 | タスク管理は既存ツールから移せない | 置き換えず、**フォーカスカードという薄い層を1枚だけ**載せる |
| 2 | バーチャルオフィスは数週間で開かれなくなる | 空間を目的にしない。**朝1分のカード更新**を毎日の起点にする |
| 3 | 「監視しません」は決裁者に売れない | 個人ではなく**プロジェクト単位の「詰まり」**を出す。監視ではなくブロッカー検出 |
| 4 | 情シスのセキュリティ審査を通らない | **通話時以外はマイクを掴まない**（OSが証明する）。ブラウザのみ。**セルフホスト可能** |
| 5 | 企業ネットワークで動かない | **TURN over TCP/443 を必須構成に**。事前診断ツール。最終手段としてテキストモード |
| 6 | 業務PCの性能で3D描画がキツい | **論理（2Dグリッド）と表現（3D）を分離**。low-poly・影なし・ベイク済み・固定カメラ・30fps上限・解像度スケーリング。3D → 2Dビュー → リストへ縮退 |

壁4〜6 は実際に会社で働いている人から挙がったもので、
**プロダクトが良くても導入されずに終わる**種類の壁。壁1〜3 と同等以上に重い。

これらの解の多くは互いに支え合っている。
たとえば「近づいても自動で通話しない」という1つの判断が、
壁4（マイクを掴まない）・壁5（通話時のみ帯域）・壁6（通話時のみCPU）に同時に効いている。
詳細は [02 Part 3](./docs/design/02-problem-solving.md) の対応表を参照。

## 接続の安全性

音声・映像が流れる以上、**どの経路で誰が中身を見られるか**を経路ごとに確定させてある。

| 経路 | 中身を見られる者 |
| --- | --- |
| ブラウザ ↔ TURN リレー | **誰も見られない**（DTLS-SRTP は端点で終端する。誤解されやすい点） |
| ブラウザ ↔ SFU（E2EE なし） | **SFU が復号できる** ← 唯一の弱点 |
| ブラウザ ↔ SFU（E2EE あり） | **誰も見られない** |

弱点は SFU 1箇所なので、そこに3つ重ねる。

1. **音声は E2EE を既定 ON** — E2EE の代償（サーバ側録画・文字起こし・MCU が使えない）は、
   **それらを最初から作らないと決めている**ので、ほぼ払わずに済む
2. **セルフホスト** — 復号するのが自社のサーバなら、そもそも「社外の誰か」がいない
3. **プライベートルームは E2EE 強制**（解除不可）

副次的に、**P2P にしていないので参加者同士に IP アドレスが渡らない**（在宅勤務者の自宅IPが同僚に見えない）。

限界も明記してある: E2EE でもメタデータは隠せない（ただし保存しない）、
ブラウザ E2EE は配信される JS に依存する。詳細は [07. 接続の安全性](./docs/design/07-security.md)。

## 技術スタック（予定）

| 層 | 採用予定 |
| --- | --- |
| フロント | Next.js 15 (App Router) + TypeScript |
| 空間描画（3D） | **Three.js**（low-poly / ベイク済みライティング / 影なし / 固定クォータービュー）、glTF + Draco |
| 空間描画（2D・縮退先） | PixiJS（WebGL / Canvas2D フォールバック）、Tiled (.tmj) 形式 |
| リアルタイム | Node + `ws`（tick 10Hz + AOI フィルタ）、Redis Pub/Sub |
| 音声・映像 | LiveKit (SFU) + coturn（**TCP/443 必須**） |
| DB | PostgreSQL + Prisma |
| 暗号化 | DTLS-SRTP + **E2EE（Insertable Streams）**。音声は既定ON、プライベートルームは強制 |
| 揮発データ | Redis（**永続化を無効化** — 原則3の技術的担保） |
| 認証 | Auth.js v5 + Google Workspace / Microsoft 365 OIDC |

構成要素はすべて OSS。**自社 VPC / オンプレへのセルフホストが可能**であることを要件にしている。
